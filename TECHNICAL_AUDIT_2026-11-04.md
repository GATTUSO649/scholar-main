# ScholarDesk Technical Audit — 2026-11-04

## Executive Summary

ScholarDesk is an established TanStack Start/React 19 application using PostgreSQL through Drizzle. The runtime, active migration chain, authentication, and payment implementation are PostgreSQL-oriented; the MySQL migration tree is documented as historical reference only. Existing authentication and M-PESA controls are materially stronger than a typical prototype: opaque hashed session tokens, server-side role checks, same-origin/CSRF controls, bounded uploads, and provider-side payment verification are present.

This iteration prioritized repeat-navigation caching and diagnostics for the currently failing file upload route. The public `/services` page measured 2.84 s for a fresh navigation on Render. Three same-origin server-function requests each took approximately 1.88–2.25 s. This is a baseline, not a Core Web Vitals measurement. The main confirmed scale/performance issue is unbounded list retrieval for requests and students. Authenticated-page timings and a post-deploy comparison were not available.

No database migrations, destructive operations, production configuration changes, dependency upgrades, or deployment were performed.

## Security and Payment Review

- **Authentication:** Sessions use random opaque tokens; only hashes are stored. Cookies are HttpOnly, SameSite=Lax, Secure in production, and server-checked for expiry. Admin sessions are shorter than student sessions.
- **Authorization:** Admin checks read `user_roles` on the server. Private request reads and file downloads derive the user from the session and check request ownership/admin access. Student delivery-file authorization also requires a paid request or matching paid payment record.
- **CSRF and input:** Same-origin mutation checks and TanStack Start CSRF middleware are enabled. Server-function inputs use Zod; file bodies are bounded before multipart parsing.
- **File handling:** Request files are stored outside the public directory and forced to download with `nosniff`. UUID storage keys are validated. The latest file API change adds sanitized failure stage/code logging and makes rollback best-effort without hiding the original error. Deploy it before relying on its new Render log fields.
- **M-PESA:** STK Push details are validated. Callback amount, phone, receipt, transaction date, and merchant/checkout references are checked. Successful outcomes are reconciled with Safaricom STK Query before marking paid; payment rows are locked during status transitions. No payment configuration or payment data was changed.
- **XSS/SQL:** React rendering is escaped by default; the code scan found no direct `eval` or `new Function`. Drizzle parameterizes application queries. No SQL injection or authorization bypass was confirmed in the reviewed paths.
- **Dependencies:** `npm audit --omit=dev` reported zero production vulnerabilities. This does not substitute for continuous full lockfile scanning.

## Performance and Data Findings

- Router intent preloading and scroll restoration are already configured; route chunks are split by the build. Authenticated routes share a persistent shell.
- React Query cache defaults now use 30 s freshness and 5 min garbage collection, with longer public-content caching and shorter request/payment policies. The admin price-visibility mutation invalidates public data. A test verifies public data is reused while payment data refetches.
- Public settings/services and settings/FAQ reads in `getPublicData` and `getPublicSiteContent` now run concurrently rather than waiting on one another. This removes a serial database round trip; production impact still needs remeasurement.
- Payment ledger reads are SQL-filtered and paginated at 50 rows. Admin requests and students remain unbounded; client-side search does not reduce their database work or payload.
- The current `postgres` pool has `max: 10`, `idle_timeout: 20`, `connect_timeout: 10`, TLS in production, and `prepare: false`. A read-only local-environment `SELECT 1` connectivity check succeeded. This does not verify Render's environment, pooler reliability, or production credentials.
- Measured Render `/services` baseline: navigation 2,840 ms; DOMContentLoaded 2,562 ms; three same-origin server-function calls took 1,882–2,252 ms. Paint entries were unavailable, so LCP, INP, and CLS are not reported. An authenticated SPA navigation measurement was not obtained.
